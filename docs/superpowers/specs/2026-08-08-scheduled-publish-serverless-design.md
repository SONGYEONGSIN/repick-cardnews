# 예약 발행을 서버리스에서 되살리기 — 설계

**날짜** 2026-08-08 · **상태** 설계 확정, 구현 전

## 왜

예약 발행이 배포 서버에서 **아예 돌지 않는다.** 화면에서 예약을 걸 수는 있는데 시각이 와도
올라가지 않는다. 원인이 넷이고 전부 "한 프로세스가 계속 돈다" 는 전제 위에 서 있다.

| 무엇 | 지금 | 서버리스에서 |
|---|---|---|
| 예약 큐 | `queue.jsonl`(디스크, append-only) | 배포마다 사라진다 |
| 카드 PNG | `<id>/1.png`(디스크) | 사라진다 |
| 깨우는 것 | 프로세스 안 `setInterval` 1분 | 그 프로세스가 없다 |
| 중복 방지 | 메모리 `Set` | 인스턴스가 다르면 안 통한다 |

## 무엇을 만드는가

### 1. 예약할 때 이미지를 Blob 에 **한 번만** 올린다

지금은 디스크에 저장했다가 **올릴 시각에 다시 읽어 또 올린다.** Blob 주소는 영구적이라 그럴
이유가 없다 — 예약 시점에 올리고 큐 항목이 그 주소를 들고 있으면 된다. 게시 경로에서
`loadImages` + 재업로드가 통째로 사라진다.

### 2. 큐 항목 하나 = Blob 파일 하나

```
scheduled/<id>/item.json   예약 내용 + 상태 + 이미지 주소들
scheduled/<id>/1.png …     올리고 나면 지운다 (item.json 은 기록으로 남긴다)
scheduled/heartbeat.json   마지막 tick 시각
```

한 파일에 모아 두면 상태를 바꿀 때 **읽고-고치고-쓰는** 사이에 다른 요청이 끼어든다. 항목마다
따로 두면 그 경합이 없다.

**항목 모양** — 지금 스키마에서 `imageCount` 대신 `imageUrls` 를 들고, `claimedAt` 이 붙는다.

```ts
{
  id, scheduledAt, caption, keyword,
  imageUrls: string[],          // 예약할 때 올린 Blob 주소
  status: "pending" | "publishing" | "published" | "failed" | "missed" | "canceled",
  createdAt, updatedAt?, message?, claimedAt?
}
```

`/api/schedule` 의 **응답 모양은 유지한다**(`imageCount` 를 `imageUrls.length` 로 계산해
내려준다) — 그러면 `SchedulePanel` 을 손대지 않아도 된다.

### 3. 밖에서 깨운다 — cron-job.org → `/api/cron/tick`

Vercel Hobby 의 cron 은 **하루 1회**가 상한이라 쓸 수 없다. cron-job.org(무료, 1분 간격)가
1분마다 이 경로를 두드린다.

- 이 경로만 **로그인 예외**로 연다(`isPublicPath`)
- 대신 **`CRON_SECRET`** 으로 막는다. 상수시간 비교(`safeEqual`)를 쓴다
- 응답은 짧은 JSON 요약 — 무엇을 올렸고 무엇을 건너뛰었는지

### 4. 중복 게시 막기 — 상태로 찜한다

인스타 호출 **전에** 상태를 `publishing` 으로 바꾸고 `claimedAt` 을 남긴다. 다음 tick 이 그걸
보면 건너뛴다. 찜한 지 **10분이 지나면 풀어 준다** — 함수가 중간에 죽으면 영원히 잠긴다.

**한계를 정직하게 적는다.** Blob 에는 원자적 비교-교환이 없다. 두 tick 이 **같은 순간에**
읽으면 둘 다 찜하고 둘 다 올릴 수 있다. cron 이 하나면 순차로 불리므로 현실적 위험은 낮지만
0은 아니다. 이 한계는 코드 주석과 `docs/deploy-setup.md` 에 적는다.

### 5. 한 tick 에 **하나만** 올린다

Vercel 함수는 300초에서 끊긴다. 캐러셀 한 건이 1~2분 걸릴 수 있어, 밀린 예약이 여러 건이면
한 번에 처리하다 중간에 끊길 수 있다 — 그러면 올라갔는지 아닌지 모르는 항목이 생긴다.

1분마다 부르므로 밀린 것은 분당 하나씩 빠진다. **끊기는 것보다 늦는 편이 낫다.**

## 그대로 두는 것

- **놓친 예약 판정**(`dueVerdict`) — 예약 시각을 한 시간 넘기면 `missed`. 로직 그대로
- **화면**(`SchedulePanel`·`schedule-view.ts`) — 응답 모양을 유지하므로 손대지 않는다
- **심장박동 경고** — 저장 위치만 Blob 으로 바뀐다. 질문이 "프로세스가 도나" 에서 "cron 이
  부르고 있나" 로 바뀔 뿐 화면 문구는 같다

## 오류가 났을 때

| 무엇이 실패하나 | 어떻게 되나 |
|---|---|
| cron 이 안 부름 | 심장박동이 낡아 화면이 경고한다 |
| 인스타 게시 실패 | `failed` + 한국어 사유. 이미지는 지우지 않는다(사람이 다시 걸 수 있게) |
| 함수가 도중에 죽음 | `publishing` 인 채 남는다 → 10분 뒤 찜이 풀려 다시 시도한다 |
| Blob 읽기 실패 | 그 tick 만 건너뛴다. 다음 분에 다시 온다 |

**이미 올라간 뒤 죽으면 다시 올릴 수 있다.** 인스타 API 는 우리가 준 컨테이너로만 게시하므로
같은 사진이 두 번 올라갈 수 있다는 뜻이다 — 위 4번의 한계와 같은 뿌리다. 받아들이는 위험이며
문서에 적는다.

## 검증

**순수 함수로 뺄 것**(RED→GREEN):
- 큐 항목 파싱·경로 만들기(`scheduled/<id>/item.json`)
- 찜 판정 — `publishing` 이고 `claimedAt` 이 10분 이내면 건너뛴다
- cron 비밀 검사 — 없거나 틀리면 거절
- 한 tick 에 하나 고르기 — 밀린 것 중 가장 먼저 예약된 것

**실측해야 하는 것**:
- 배포 서버에서 예약을 걸면 Blob 에 `item.json` 과 PNG 가 생기는가
- `CRON_SECRET` 없이 `/api/cron/tick` 을 부르면 거절되는가
- **cron-job.org 가 실제로 부르고, 예약한 사진이 인스타에 올라가는가** ← 이것이 성공 기준
- 심장박동이 갱신되는가

## 하지 않는 것

- 여러 건 동시 게시 · 재시도 큐 · 원자적 잠금(Blob 이 지원하지 않는다)
- 화면 개편 · 예약 수정 기능
- 인스타 토큰 자동 갱신 (3단계)
